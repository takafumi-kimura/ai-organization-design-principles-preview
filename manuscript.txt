序章　不確実性に向き合う——XPからAI組織へ

私は、劇団四季の[『ノートルダムの鐘』](https://www.shiki.jp/applause/notredame/)が好きだ。物語の始まりと終わりに、人間と怪物の違いを問いかける。同じ問いが、物語を経たあとには違って聞こえる。その構造へのオマージュとして、本書では問いをこう置き換えてみたい。

答えてほしい謎がある。
人間とAI、どこに違いがあるのだろう。

仕事を生み出し、結果を確かめ、次の一手を考える。そのどこまでをAIに委ねられるのか。この問いを頭の片隅に置いて、まずは、開発チームを作ろうとしたところから話を始めたい。

もともと目指していたのは、少数精鋭で最強のソフトウェア開発チームを作ることだった。

そのチームをどう作るかを考える出発点に、ソフトウェア開発の不確実性があった。

### ソフトウェア開発は、不確実性と向き合う仕事

何を作れば利用者の課題を解決できるのか。選んだ技術や設計で、本当に実現できるのか。変更を加えたとき、別の場所に問題が起きないか。

ソフトウェア開発では、着手する時点ですべての答えが揃っているわけではない。作って初めて分かることがあり、使ってもらうことで変わる要求もある。

だからこそ、開発の重要な仕事は、不確実性をいかにコントロールするかにある。分からないことを早く確かめ、間違いの影響が小さいうちに気付き、学んだことを次の判断へ反映する。

この問題に向き合う考え方が、アジャイルソフトウェア開発である。小さく作り、動くソフトウェアからフィードバックを得て、計画と実装を更新する。アジャイル宣言の原則にも、要求の変化への対応、短い間隔での提供、技術と設計への継続的な注意、チームの振り返りが示されている。[アジャイル宣言の原則](https://agilemanifesto.org/iso/ja/principles.html)

### XPは、フィードバックを徹底する

アジャイルには複数の手法がある。その一つが、Extreme Programming（XP）である。

XPは、テスト、ペアプログラミング、継続的インテグレーション、リファクタリングなど、日々の開発を支える具体的な実践を組み合わせる。例えばテストファーストでは、期待する振る舞いを先にテストで表し、実装からすぐにフィードバックを得る。継続的インテグレーションでは、小さな変更を頻繁に統合して検証し、問題の発見を先延ばしにしない。[Agile AllianceによるXPの解説](https://agilealliance.org/glossary/xp/)

私は、数あるアジャイル手法の中でも、XPを本当にエクストリームな、究極の開発手法だと捉えている。

有効な実践を、徹底して、短い間隔で繰り返す。その徹底によって、不確実性に向き合い続けられるところに惹かれている。

もともとは、このXPを人間のチームを中心に実践していた。設計・実装・テスト・レビュー・フィードバックを高速に回しながら、少人数でも高い生産性と品質を実現しようとしていた。

その成果を捉える指標として考えていたのが、デリバリーの速さと安定性を見るFour Keysである。今は、この目標をAIチームの設計へ引き継いでいる。指標を自動計測し、結果から仕事の進め方を改善するAI組織を作る。第16章で、この関係を具体化する。

### XPの自己相似性——同じ構造を、異なる規模へ

この実践を別の対象へ広げる手掛かりも、XPの中にある。自己相似性（Self-Similarity）という原則である。

XPには、何を大切にするかを示す「価値」、日々行う「プラクティス」、両者をつなぐ「原則」がある。原則は、既存の手順がそのまま当てはまらない状況で、実践を組み立てるための考え方となる。[BeckとAndresによるXPの説明](https://www.informit.com/articles/article.aspx?p=367636)

Kent BeckとCynthia Andresの『Extreme Programming Explained 第2版』では、第5章の原則の一つとしてSelf-Similarityが扱われる。名前の背景には、異なる大きさに似た形が現れる、数学の自己相似性がある。XPでは、ある場面で働いた解決の構造を、規模の異なる場面にも応用してみる考え方として使う。原典は、テストと実装の小さな循環から、週単位のストーリー、四半期のテーマまで、似た開発のリズムを見いだしている。[原典第5章の公開抜粋](https://ingenieria-de-software-i.github.io/assets/bibliografia/xp-principles-and-practices.pdf#page=8)

本書では、これを「対象や規模が変わっても、有効だったフィードバックの構造を保つ」という設計の手掛かりとして使う。例えば、一つの関数ではテストで期待を表し、機能全体では受け入れ条件で期待を表す。確かめる対象は変わっても、期待を明らかにしてから作り、結果を照合し、次の修正へ返すという形は共通する。

自己相似性を応用するときは、フィードバックの構造を保ちながら、確かめる内容と周期を対象に合わせる。関数のテストで正しい戻り値を確認できても、機能が利用者の課題を解決したかを知るには、利用状況からのフィードバックも必要になるからである。Beckも、ある文脈で成功した構造が別の文脈でも成功するとは限らないと述べている。応用先で何を変え、何を保つかを考え、効果を確かめるための出発点である。[原典の自己相似性の説明](https://ingenieria-de-software-i.github.io/assets/bibliografia/xp-principles-and-practices.pdf#page=9)

### AIにも、不確実性がある

本書の執筆に至る半年ほどで、開発を担う主体についての考えが大きく変わった。

AIは、設計案もコードもテストも生成できる。一方で、その出力が常に正しいとは限らない。要件を取り違えることもあれば、もっともらしい説明とともに不具合を持ち込むこともある。評価を担当するAIの判断にも、誤りや見落としがある。

ソフトウェア開発にもともとある不確実性に、AIの振る舞いの不確実性が重なる。

そこで考えたのが、人間の開発で働いた不確実性への向き合い方を、AI組織にも適用できるのではないか、ということだった。

例えばAIが変更を生成したら、小さな単位でテストと評価に通す。問題があれば、その根拠を次の生成へ返す。一度で正解が出ることを前提にせず、短いフィードバックの循環で誤りを見つけ、修正する。人間のチームで重視していた原理を、AI組織にも組み込むのである。

私は、この転換を、XPの自己相似性をAIによる開発へ適用したものと捉えている。

ここで変わるのは、時間やチームの規模だけではない。仕事を担う主体も、人間からAIへ変わる。その新しい文脈へ、期待を定義し、小さく作り、結果を評価し、修正する構造を移す。これは、原典の原則を土台にした本書の応用である。

### XPを、AI組織の仕組みとして実装する

ここから、**「AIにXPを実践させ、人間がそのAIチームをマネジメントする」**という構造を発想した。

そのためには、XPの実践を、AIが従う実行可能な仕組みとして設計する必要がある。

本書では特に、小さな変更、短いフィードバック、自動テスト、継続的な改善を、AI組織の構造へ落とし込む。利用者との対話や、何を価値とするかの判断も、その構造へ要求と評価基準を与える仕事として位置付ける。

AIに渡す仕事は、生成と評価の二つに限定する。どの入力を渡すか、どの評価を通すか、どの条件で修正に戻すか、いつ停止して人間へ判断を戻すかは、決定論的なハーネスが制御する。自動テストの実行や結果の記録も、この基盤が担う。

AIの出力が不確実であっても、その出力を扱う手順と権限の境界は、コードとインフラによって制御できる。ただし、評価を必ず実行できても、その評価基準に抜けがあれば欠陥は通過してしまう。手順を守らせる制御と、欠陥を見つけられる評価の両方が必要になる。だから、生成と評価を細かく分け、結果を観測し、評価の仕組みも改善し続ける。

学習に応じて開発の進め方を変えることと、実行中のワークフローを確実に守らせることは両立する。変更案を検証し、定義された手順で採用することで、AI組織そのものを改善していく。

自己相似性を、この文脈で実装する形が「生成と評価をAIへ渡し、その循環をハーネスで制御する」という本書の設計である。XPの原則から着想し、AIの性質に合わせて入出力の契約、実行基盤、権限の境界を具体化する。

同じ発想は、後半でもう一度現れる。コードを評価する仕組みも、そのAI組織をマネジメントする仕事も、生成・評価・フィードバックの構造へ分解できるのではないか。本書は、その自己相似な構造を一段ずつ組み立てていく。

### この本で作りたいもの

少数精鋭という目標は、最初から変わっていない。

変わったのは、その実現方法である。少人数の人間がXPを実践する構造から、少人数の人間が、XPの原理を組み込んだAIチームを設計し、マネジメントする構造へ移った。

少数の人間がEngineering Managerとして、それぞれ高性能なAIチームを率いる。

それが現在考えているAI組織の形である。

本書は、ソフトウェア開発とAIの不確実性に向き合うために、XPの原理をAI組織へ適用し、そのAI組織を実際に作るための方法を記すものである。

生成と評価、決定論的なワークフロー、ハーネス、可観測性、そして人間の責任。それらを一つの実行可能なAI組織として設計する。それが、本書で扱うSoftware-Defined Engineering Organizationである。

AI組織とは、生成と評価を担うAI、仕事をつなぐコード、評価定義や実行記録、隔離環境を合わせた仕組み全体を指す。その中で、画面の開発など一つの成果に責務を持つ単位を、AIチームと呼ぶ。人間は、その目的と委譲する範囲を定め、仕組みを設計・運営する。

本書では、AIへの入力になり得る個人情報を扱わない。設計・実装・評価には、個人情報を含まない資料や検証用データを用いる前提で説明する。

### 本書の疑似コードの読み方

本書の疑似コードは、仕事の流れをひと目で捉えるためのPythonである。AIの仕事をai.generate（生成）とai.evaluate（評価）で示し、分岐、反復、停止はコードとして書く。細かな実装は省き、流れの理解を助ける箇所だけに載せる。

決定論的とは、固定した定義、状態、検証済みの入力に対して、次に何をするかをコードの規則で決めるという意味である。例えば、同じワークフローの版と再試行回数でFAILを受け取れば、コードは同じ差し戻し先を選ぶ。AIがその後に生成する修正版にはばらつきがあっても、戻す相手や停止する条件までAIの解釈で変わることはない。

contractは仕事を始める前に定めた入出力と評価条件、policyは運用のルールを表す。requireは条件を満たさなければ停止し、validateはデータの形式を検証する。これらは流れを示すための抽象であり、そのまま動く実装例ではない。

すべてのAI呼び出しは、入出力の検証、権限、時間・費用の上限、実行記録を備えたハーネスを通す。各例では共通処理を繰り返し書かない。タイムアウトや不正な返答を、PASSやSKIPとして先へ進めることはない。

テストや形式の確認など、コードで判定できる条件はコードで確かめる。意味内容の判断が必要な部分をAIの評価へ渡し、その結果から次の工程を決める。

第1章　開発の主体を、人間からAIへ

不確実性に対応するために、小さく作り、確かめ、フィードバックを返す。その循環をAI組織で実装すると、開発の役割分担はどう変わるのか。

本書で扱う構造では、AIが設計案、コード、テストケースを生成し、定義された観点で成果物を評価する。テストの実行、評価結果の検証、次の工程への引き渡しはハーネスが担う。

一度コードを生成して終わりにはしない。変更をテストと評価に通し、問題があれば根拠を返して修正させる。

実装 → 評価 → フィードバック → 修正 → 再評価

という短いループを、決定論的なハーネスが高速に回す。

このループの中でAIに渡す仕事は、生成と評価の二つだけである。実装と修正は生成に、観点と証拠に基づく判断は評価にあたる。次の工程へ進むか、修正へ戻すかは、検証済みの結果を受けてコードが決める。

### 修正の循環を、回数のあるループにする

一つの小さな仕事を、決めた回数だけ試す。check_changeは、生成した版に対するテストと全必須観点のAI評価をまとめた処理を表す。テストの失敗はFAIL、証拠不足はNEEDS_INPUTとして返す。実行エラーは停止する。

```python
def develop(task, contract):
    feedback = None
    for _ in range(contract.max_attempts):
        change = ai.generate(task, feedback, contract=contract)
        result = check_change(change, contract)
        if result.status == "PASS":
            return change
        require(result.status == "FAIL")
        feedback = result.findings
    stop("修正回数の上限")
```

通過なら成果物を返し、FAILなら指摘を次の生成へ渡す。NEEDS_INPUTではrequireが処理を止め、入力の補完へ引き渡す。試行上限もコードが守らせる。AIの「完成した」という説明だけで、ループを抜けることはできない。

小さな変更を繰り返し、自動テストと評価から学ぶ。AIの出力に不確実性があるからこそ、こうしたXPの原理が重要になる。

XPの原理を、AIとハーネスからなるチーム全体の振る舞いにする。

これが最初の大きな転換である。

第2章　AIチームのEMになる——APIで制御と計測を設計する

では、人間のエンジニアは何をするのか。

重要になるのが、Engineering Manager（EM）という役割である。本書では、AIチームの目的、仕事の進め方、品質と費用に責任を持つ役割として使う。一人のソフトウェアエンジニアでも、自分のAIチームを設計・運営することで、この役割を担う。

EMの仕事を、生成されたコードの全件確認だけで成り立たせることはできない。日常の検証を仕組みに組み込み、変更の影響や評価の弱点に応じて、サンプリングや重要箇所のレビューを行う。

自分が担当するAIチームの振る舞いと、その結果に責任を持つ。

チームの仕事の進め方と成果に責任を持つ、という点は、人間のチームをマネジメントするときと共通している。AIチームでは、その進め方をコード、評価基準、実行基盤として明示的に設計できる。

改善の対象も、個々のコードから、そのコードを生み出す仕組みへ広がる。欠陥を修正するとともに、なぜ生成され、なぜ見逃されたかを調べ、次の仕事に生かす。

### 管理のきっかけを、観測値から定義する

EMがAI組織全体を見るために、何を異常とするか、どの状態で仕事を止めるかもコードにする。例えば、費用が上限に達したら新規の着手を止め、重大な見逃しが見つかったら公開を止める。再試行が増えたら、対象の履歴を集めて改善を始める。

停止する対象や改善を始める条件が明示され、根拠となった観測値とルールの版も残る。EMはこのルールと観測の妥当性を見直す。

### なぜ、APIと決定論的なワークフローを選ぶのか

ここで、本書が前提とするAIの使い方を明らかにしておきたい。

本書では、CodexやClaude Codeのサブスクリプションを中心に、指示書を渡して一連の仕事を任せる運用から、モデルAPIを従量課金で呼び出し、決定論的なワークフローで生成と評価をつなぐ運用へ進む。

この構成でも、コードの調査や実装にはコーディングエージェントを使う。小さな評価観点はモデルAPIへ直接渡し、既存コードのリバースエンジニアリングや複数ファイルにまたがる修正は、OpenCodeなどへ一つの仕事として依頼する。エージェントにも従量課金のモデルAPIを接続し、外側のワークフローが仕事の開始条件、成果物の受け取り、次の工程への通過を管理する。

APIはモデルへの接続・課金の経路であり、エージェントはモデルとツールを組み合わせて仕事を進める実行器である。エージェント経由では内部の探索や修正の順序を委ねるため、モデルAPIを直接呼ぶ場合と同じ粒度ですべてを制御できるとは扱わない。第3章で、この境界と利用条件を具体化する。

AI組織を継続的に運営するには、何を実行したか、どの条件で成功・失敗したか、どこを変えれば改善するかを、仕事の単位で確かめられる必要がある。そのために、工程、入出力、評価、モデル選択、記録を、自分たちで設計できる形にする。

APIを選ぶ理由は、工程ごとの入出力と実行条件を設計し、AI組織の制御とデータを自分たちで管理するためである。直接呼ぶ評価では観点ごとに、エージェント経由では依頼した仕事と取得できる内部記録を結び付けて扱う。特に重視するのは、評価観点と評価結果をRDBなどで厳密に管理し、どの定義がどの条件で有効だったかを機械的に検証できる状態を作ることだ。

評価観点と評価結果を、効果を機械的に検証できる構造化データとして管理する。

この設計によって、改善をデータに基づいて進められるようになる。さらに、蓄積したデータを使って改善案を生成し、その効果を評価する仕事もAIへ委ねられる。後続の章で扱うObservabilityと評価システムの改善は、ここからつながっている。

### 指示が読まれたことと、工程が実行されたことを分ける

Markdownに「実装したらレビューし、問題があれば修正する」と書く。その文章を解釈し、いつレビューし、何を確かめ、どこで完了とするかまでAIへ任せると、ワークフローの進行にも推論の不確実性が入り込む。

指示書が読み込まれた記録は、必要な工程が実行された証拠にはならない。「レビューしました」という返答だけでは、どの版の成果物に、どの評価観点を適用し、どの証拠で判断したのかを確かめられない。Claude Codeの公式資料も、CLAUDE.mdはコンテキストとして扱われ、設定のように実行を強制するものではないと説明している。[指示と強制される設定の違い](https://code.claude.com/docs/en/memory)

そこで本書では、レビューを生成から分けた評価工程として呼び出す。観点ID、指示の版、対象となる成果物の版、モデル構成、PASS・FAILなどの結果と根拠を関連付ける。必須評価が揃うまで先へ進めない条件は、コードにする。

指示書の形式そのものが問題なのではない。手順を文章だけで定義し、その履行の判断までAIに委ねることが問題なのである。Markdownは専門知識や背景の説明に使い、工程の実行と通過条件はソフトウェアで強制する。

### 評価の定義と結果を、比較できるデータにする

例えば、「画面の状態表示を、色以外の手掛かりでも判別できるか」という評価観点を作る。この観点にIDを付け、指示を変えるたびに新しい版を登録する。評価結果は、そのIDと版、評価した成果物、実行条件へ結び付けて残す。

RDBでは、例えば次の四つの記録を関連付ける。指示の本文や判断の説明は自然言語でよい。その周囲に、同じ意味で検索・集計できる項目と、項目間の関係を定義する。

| 記録するもの | 主な内容 | 検証にどう使うか |
| --- | --- | --- |
| 評価観点の定義 | 観点ID・版、対象、指示、合否条件、出力スキーマの版 | どの評価基準を適用したかを特定する |
| 評価の実行 | 実行ID、観点ID・版、成果物と入力の版、モデルと設定、時刻、費用、実行の成否 | 条件を揃えて比較し、実行できなかった評価も把握する |
| 評価結果 | 実行ID、PASS・FAILなどの判定、指摘、証拠の参照 | 各観点の判断を集計し、元の証拠まで辿る |
| 効果検証用のケース | ケースID・版、対象への参照、確認済みの期待判定と根拠 | AIの判断が正しかったかを照合する |

厳密に管理するとは、必要な項目があり、値の種類が決まり、どの定義・実行・成果物の記録なのかが一意に辿れることである。公開済みの評価定義は上書きせず、新しい版として追加し、結果は実行IDへ結び付ける。ハーネスが返答のスキーマと参照先を検証し、モデル構成や費用などの実行情報を記録する。

「だいたい問題ありません」という文章から、後で合否を読み取る運用にはしない。判定を所定の値として受け取り、指摘と根拠は別の項目に保持する。未実施や実行エラーは評価結果と区別し、記録が欠けた仕事を通過させない。具体的なスキーマとJSON・RDBの使い分けは、第6章で扱う。

### 評価観点を変えた効果を、機械的に確かめる

先ほどの状態表示の評価観点を、v3からv4へ改善するとしよう。品質の条件を変えず、すべての状態を照合する手順や、形の違いで判別できる場合の扱いを明確にする。

通常の仕事では、一つの生成結果を必要な観点ごとに検証する。ここでは、その評価観点自体の性能を測るため、正解を確認した複数のケースを使って比較試験を行う。

比較には、改善案の生成に使っていない、期待する判定を事前に確認した100件の画面ケースを使う。色だけで区別している欠陥例を20件、文字や形で正しく区別できる正常例を80件用意する。期待判定とその根拠は、人間による確認や検証済みのテストなどで確定し、今回測定するAIの判断とは独立して管理する。同じAIの判断をそのまま正解にすると、そのAIと同じ見逃しをする評価ほど正しいと数えてしまい、欠陥を検出する能力を測れなくなるためである。

同じ成果物、入力、モデル構成で、各ケースをv3とv4それぞれ3回ずつ評価する。実行と結果をケースIDへ結び付ければ、コードで次のように集計できる。以下は全件で有効なPASSかFAILを得たと仮定した説明用の数値であり、実モデルの測定結果ではない。

| 比較する指標 | v3 | v4 |
| --- | --- | --- |
| 見逃し：欠陥例をPASSにした回数 | 12 / 60回（20%） | 3 / 60回（5%） |
| 誤検知：正常例をFAILにした回数 | 24 / 240回（10%） | 6 / 240回（2.5%） |

欠陥例は20件を3回評価するので60回、正常例は80件を3回評価するので240回が分母になる。ケースの期待判定とAIの判定を照合し、観点の版ごとに集計する処理は、決定論的なコードとして繰り返し実行できる。費用や所要時間、繰り返した際のばらつきも同時に比較する。

これが、評価システムをデータドリブンに改善するということである。判定を甘くすればPASS率は上がるため、通過率だけでは改善と呼べない。見逃しと誤検知を分け、何件を評価できたかも確認する。判断不能や実行エラーは別に集計し、SKIPをPASSへ混ぜない。

機械化するのは、条件を揃えた実行、記録の照合、指標の計算である。期待判定の妥当性や、評価セットが実際の仕事を代表しているかは、引き続き検証する。数値が良くなった案も、改善案の生成に使っていないケースで確かめ、採用後の結果まで観測する。

### 半年前の指示を、残すか捨てるか判断できるか

例えば、半年前のモデルがよく間違えたために、長い注意書きや追加のレビュー手順を加えたとする。新しいモデルでは、その注意書きが不要になっているかもしれない。別の表現の方が有効になったり、以前の指示同士が干渉したりする可能性もある。

しかし、指示ごとの実行と効果を測っていなければ、消してよい根拠がない。失敗のたびに指示を足し、昔の指示は念のため残す。評価観点や工程も増え続ける。こうして、AIへ渡すコンテキストと運用の複雑さを減らせなくなる。

会話の履歴だけから、どの指示がどのモデルで有効だったかを後から切り分けるのは難しい。モデル名の記録で分かるのは、誰が実行したかまでである。結果が良くなっていても、モデルの変更、指示の変更、仕事の難易度のどれが効いたのかは、その記録だけでは判断できない。指示の効果を知るには、比較する条件と結果を対応付ける必要がある。

本書の構成なら、同じ評価セットで「旧モデル・指示あり」「旧モデル・指示なし」「新モデル・指示あり」「新モデル・指示なし」を比較できる。比較するモデルと指示の有無以外の入力や設定を揃え、複数回の実行で見逃し、誤検知、費用、所要時間と、そのばらつきを測る。モデルを替えた効果と、指示を外した効果を分けて確かめるのである。OpenAIのモデル移行ガイドも、古い指示をすべて引き継ぐのではなく、必要な契約を保つ小さなプロンプトから評価し直す方針を示している。[モデル更新時のプロンプトの見直し](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.5)

不要と分かった説明、重複した評価、役割を終えた工程は、既知の失敗例を含む検証を通して削除・統合する。守るべき品質条件や権限の境界は保ち、採用する定義の版を切り替える。第6章から第8章では、そのためのデータ管理、評価の改善、用途別のモデル選択を扱う。

AI組織の持続可能性は、指示を足せることだけでなく、根拠を持って減らせることにも支えられる。

### 観測したデータで、改善する仕事もAIへ渡す

構造化した記録があれば、「どの観点の、どの版が、どのケースを見逃したか」をコードで抽出できる。その結果と、対応する評価定義や証拠を、改善を担うAIの入力にする。

例えば、AIが見逃しの傾向を分析し、評価観点v4の候補を生成する。別の評価工程が、候補が元の品質条件を保っているか、対象や指示が明確かを評価する。その後、ワークフローが候補の生成に使っていない評価セットで新旧を実行し、見逃し・誤検知・費用を比較する。

AIが「改善した」と説明するだけでは採用しない。先に定めた検証条件を満たした候補だけを、変更管理の工程へ送る。AIが担うのは改善案の生成と評価であり、比較の実行、採否の条件、稼働中の定義の切り替えはコードが制御する。

この循環に必要なのがObservabilityである。入力、評価結果、差し戻し、修正版、その後の結果を同じ仕事として辿れなければ、何が効いたかを説明できない。観測の設計は、改善を行う人間にもAIにも、必要な入力を供給する仕事になる。

Observabilityは、AI組織の改善を駆動するための基盤である。

第5章で仕事と判断の可観測性を、第6章で評価観点と結果のデータ管理を、第7章でそのデータを使った評価システムの改善を具体化する。APIで呼び出すこと、構造化して観測すること、改善をAIへ委ねることは、一つの設計としてつながっている。

### 二つのアプローチを比較する

ここで比較するのは、追加の制御・計測を作らず指示書中心で進める運用と、それらを実装したAPI中心の運用である。CodexのCLIにもClaude Codeにも、利用可能なモデルを指定・変更する機能がある。[Codexのモデル設定](https://learn.chatgpt.com/docs/models)、[Claude Codeのモデル設定](https://code.claude.com/docs/en/model-config)

実行モデルや利用量を含むテレメトリーも取得できる。製品に観測機能がないわけではない。その記録を、評価観点や指示の版、成果物、後続の結果へ結び付けて初めて、AI組織の改善に使えるデータになる。[Codexの実行記録](https://learn.chatgpt.com/docs/config-file/config-advanced#observability-and-telemetry)、[Claude Codeの監視機能](https://code.claude.com/docs/en/monitoring-usage)

| 比較する点 | サブスクリプションのエージェント中心 | API＋決定論的なワークフロー |
| --- | --- | --- |
| 仕事の進め方 | 指示書を解釈したエージェントが工程を進める | コードが工程を呼び出し、遷移・再試行・停止を決める |
| 完了の確認 | 会話や実行ログから、手順を守ったか確認する | 必須評価の結果と証拠を検証し、揃うまで通過させない |
| 評価データの管理 | 指示書と会話の記録が中心。観点と結果の対応付けは別途必要 | 評価定義と結果をスキーマで検証し、IDと版でRDBなどへ関連付けて保存する |
| 観測の単位 | セッションや呼び出しの記録。観点ごとの効果比較には追加設計が必要 | 一つの評価から、入力・モデル構成・成果物版・証拠・費用・後続の結果まで辿れる |
| 効果の検証 | ログの読解と個別の試行を中心に確かめる | 確認済みの期待判定と結果を照合し、見逃し・誤検知・費用をコードで比較する |
| モデルの選択 | 製品の設定で変更できる。用途別の選択根拠は別途管理する | 用途ごとの測定値と条件に基づく選択を、コードで実行する |
| モデル更新への対応 | 指示ごとの再評価がなければ、古い指示を残しやすい | 同じ評価セットで新旧モデルと指示の効果を比較する |
| 指示・評価・工程の整理 | 効果が分からないまま、念のための追加が積み重なりやすい | 検証結果から削除・統合し、採用する定義を版管理する |
| 改善活動 | 記録を人間が読み、次の指示や運用を考える | 構造化データからAIが改善案を生成・評価し、コードが実測による検証と反映を制御する |
| 費用と運営 | プランの利用枠を中心に使い、依頼と結果確認を運用する | APIの従量費用に加え、制御・計測基盤の構築と保守を担う |
| 改善を反映する範囲 | 各セッションへの指示と、人間による運用 | AI組織の定義を更新し、その後の対象となる仕事へ反映する |

エージェントにフックや外部の制御を組み込み、必須処理と記録を実装する道もある。例えばClaude Codeのコマンド型フックは、所定の時点で処理を実行するための仕組みである。こうした制御を作り込む方向は、本書の設計とつながっている。[フックによる実行制御](https://code.claude.com/docs/en/hooks-guide)

課金方式だけで決定論性は決まらない。APIでも、長い指示を一度渡してすべて任せれば、同じ問題が残る。本書は、APIを窓口として、生成と評価を細かく分け、それらを結ぶ制御と計測を実装する方法を選ぶ。

同様に、会話ログをRDBへ保存するだけで、効果検証が可能になるわけではない。評価の単位とスキーマを定め、定義・実行・結果・検証用のケースを結び付ける。その設計によって初めて、記録が継続的な改善に使えるデータになる。

### APIの費用を、AI組織の運営費として捉える

細かな評価を大量に呼び出す構成では、APIの利用額が、サブスクリプションの利用枠内で働く場合より高くなることがある。モデル、処理量、契約条件によって差は変わり、実行基盤の構築・保守費用も必要になる。CodexにもClaude CodeにもAPI課金で使う経路があるため、同じ製品でも、利用枠を使う場合とAPIの使用量に応じて支払う場合では費用の見積もり方が変わる。製品名に加えて、実際に使う契約と課金経路を確認する。[CodexのAPI課金](https://learn.chatgpt.com/docs/pricing)、[Claude Codeの費用管理](https://code.claude.com/docs/en/costs)

それでも、本書で作りたいのは、生成、評価、フィードバック、モデル配置、学習のための記録が連動して働くAI組織である。APIの費用は、そのAI組織を稼働させる運営費として捉える。

一度改善した評価基準は、以後の対象となる仕事へ適用される。評価の一部を、必要な品質を満たす安価なモデルへ移せば、その工程を呼ぶたびに効果が及ぶ。人間は各依頼への指示を繰り返すことから、仕事を生み出し続けるAI組織を設計・改善することへ、働きかける対象を広げられる。

私は、ここに、エージェントで目の前の仕事を速くするだけでは届かない、生産性の大きな転換があると考えている。その効果は、Four Keys、品質、完了した仕事あたりの総費用、人間が介入する時間で確かめる。第6章のコンテキストキャッシュや第8章の用途別モデル選択は、このAI組織を持続的に運営するための費用設計でもある。

費用をかけて作るのは、継続的に成果を出し、その仕事の進め方も改善できるAI組織である。
